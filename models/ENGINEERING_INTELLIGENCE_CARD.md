# Card — Engineering Intelligence (Phase 3)

**Task:** turn retrieved evidence into engineering conclusions a maintainer
can act on *and check* — what probably broke, why, what to look at first,
how bad it is, and whether this has happened before.

Phase 3 adds **no new retrieval source**. It reasons over what Phases 1–2
already index (code, commits, pull requests, resolved issues).

## The constraint everything else follows from

**A conclusion that cannot name its evidence is not allowed to exist.**

That is enforced in three places, not requested in a prompt:

1. `Claim.__post_init__` raises if constructed without evidence. There is
   no code path anywhere in the phase that can express an unfounded
   conclusion, because the type refuses to hold one.
2. `Evidence.from_chunk()` is the only sanctioned way to build code /
   commit / issue evidence, and it can read nothing but a retrieved chunk.
   If it's in an `Evidence`, it was in the index.
3. `report.py` renders every factual reference itself. The LLM writes prose
   (summary, reasoning, next step); Python writes anything that names a
   commit SHA, issue number, file, line span, or release tag. A model
   cannot fabricate a hash into a section it doesn't author.

The result: GHIC can be **wrong** — a correlation can mislead — but it
cannot be **unfounded**, and any statement is checkable in seconds.

## Two deliberate refusals

### No LLM in the analysis path

A root cause generated by a language model is a fluent guess whose
confidence tracks its phrasing. One derived from *"this commit modified the
file this issue names, three days before it was filed"* is a lead a
maintainer verifies in ten seconds. The LLM keeps its existing job; the
findings are computed in `analysis.py` where they can be unit-tested.

This also means Phase 3 costs **milliseconds, not seconds** — no extra
network call in the webhook path.

### No uncalibrated numbers dressed as measurements

The spec asks for `Authentication 92%`. This project has twice refused to
ship exactly that kind of number (PRIORITY_CARD.md, SEVERITY_CARD.md: *"a
fabricated number wearing a UI"*). The compromise, which keeps the feature
without the dishonesty:

- Every **input** is a measured count over indexed history — issues
  attributed to a component, how many were regressions, median days to
  close. Those are facts and are reported alongside any score.
- The composite is a **heuristic index, not a probability**. Not calibrated
  against ground truth, because no ground truth for "component health"
  exists in this corpus. Its formula is published in `health_score`'s
  docstring so it can be argued with.
- Below `MIN_ISSUES_FOR_SCORE` (8) observations, **no score is produced at
  all** — `health_band` returns `"insufficient history"`. Three issues
  cannot distinguish a fragile component from an unlucky one, and a 67%
  from three data points is the false precision this project exists not to
  ship. Repository `risk_index` follows the same rule and returns None.

If that distinction stops being maintained — if the index starts being
consumed as though validated — it should stop shipping.

## How the findings are derived

| Finding | Signals (all observed) | Status |
|---|---|---|
| **Possible root cause** | commit within 45d of the issue **and** file/component overlap with retrieved code; identifier match strengthens it | Inferred |
| **Regression signals** | reporter's own words ("used to work"), release within 14d, a related commit that itself fixed a regression | Verified (words) + Inferred (windows) |
| **Recurring problem** | ≥2 retrieved prior issues in the same area | Inferred |
| **Engineering impact** | components implicated by retrieved code; count of prior issues in the area | Verified + Inferred |
| **Timeline** | every dated retrieved artifact, anchored at this issue | Pure fact |
| **Investigation plan** | ordered steps, each naming a real artifact | Mixed |

**Root cause needs two signals, not one.** A recent commit somewhere
unrelated is not a lead, and neither is an old commit in the right file.
Both must hold (`test_root_cause_requires_file_overlap`).

**Certainty is never asserted.** `hedge()` maps confidence to
`likely` / `possibly` / `may be` in code, so a later prompt edit can't
weaken it. A test asserts no root-cause claim contains "caused by".

**Impact stays engineering-side.** "Customer impact" and "business risk"
are not derivable from a repository — a codebase does not know who its
users are. The LLM layer already produces a grounded business-impact read
from the *issue's own text* (Phase 1.5); this doesn't duplicate or
contradict it. A test asserts the words "customer" and "revenue" never
appear in an impact claim.

## Duplicate intelligence beyond similarity

Similarity answers "are these worded alike", which isn't the maintainer's
question. `classify_relationship` returns one of four labels because the
correct action differs completely:

- **probable duplicate** — close and link. Requires high similarity **and**
  component overlap; the label invites closing a real bug, so it needs the
  strongest evidence.
- **regression family** — checked *before* duplicate, deliberately: two
  reports of the same recurring break are **not** duplicates. Closing the
  second destroys the signal that it happened twice.
- **recurring problem** — the area keeps producing issues; the fix may be
  structural.
- **related issue** — the safe default everything ambiguous degrades to.

`cluster_history` groups on **component, not text**: two issues described
completely differently but fixed in the same module belong together, and
text clustering never finds them.

## Attribution linkage

Component health is measurable only because commits name both the files
they touched *and* the issue they closed (`fixes #355`). That gives
issue → component from evidence rather than from guessing at a title. An
issue never linked by a commit is **not attributed** rather than assigned
somewhere plausible (`test_unlinked_issues_are_not_attributed`).

## Silence over filler

A finding with no claims renders nothing. An analysis with no findings adds
no sections, and the comment degrades exactly to the Phase 2 shape. A
one-row timeline containing only "this issue was reported" is suppressed.
Empty headings under confident titles are how a tool looks thorough while
saying nothing.

## Configuration

```bash
GHIC_ENGINEERING_INTELLIGENCE=false   # off by default
```

Requires `GHIC_USE_REPO_INTELLIGENCE` — it reasons over what that
retrieves and has nothing to work from otherwise. Failure is absorbed at
two levels (the analyzer catches internally; the webhook wraps it anyway),
degrading to the Phase 2 comment.

## What isn't built

**Feature 10's dashboard UI.** `summarize_repository()` and
`ComponentAnalyzer.hotspots()` compute the analytics; the React dashboard
is a separate repository and rendering them there is separate work.

**Feature 8's knowledge graph is implicit, not materialized.** The
issue → component → file → commit → PR relationships are traversed at
analysis time from retrieved chunks. A persisted graph store would be
justified by queries this phase doesn't yet make, and building one now
would be infrastructure without a consumer. The traversal logic lives in
`components.ComponentAnalyzer.analyze` and `clustering.cluster_history`;
materializing it later doesn't change any caller.

**Feature 12's "engineering memory" is derived, not learned.** Statements
like "this repository frequently experiences CSV parsing regressions" come
from `ComponentStats` computed fresh over indexed history — there is no
stored model that drifts, and no training loop to validate. That is the
honest version of the feature; a learned one would need ground truth this
corpus doesn't have.
